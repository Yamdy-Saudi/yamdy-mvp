# HungerStation capability matrix

Checked 2026-09-26 against the [official HungerStation Partner API v2.0.2](https://developer.hungerstation.com/api-specifications), [developer portal](https://developer.hungerstation.com/en), [catalog use cases](https://developer.hungerstation.com/en/documentation/catalog-api-use-cases), and [outlet integration guide](https://developer.hungerstation.com/en/documentation/outlet-management-api-how-to-integrate). The portal explicitly frames this Partner API as **Q-Commerce / Local Shops**. A documented endpoint is VERIFIED as a public contract, **not** verified for Yamdy's restaurant account, market, credentials, or production entitlement. That applicability gate remains open for every external operation.

Classifications: **VERIFIED** = specifically documented public endpoint/contract (still subject to account access); **UNVERIFIED** = no adequate public proof for the screen's exact behavior or restaurant applicability; **NOT PUBLICLY SUPPORTED** = public docs expose a narrower operation or explicitly state it is unavailable; **MOCK FOR MVP** = internal demo workflow only, clearly labeled. A row can pair contract classification with an MVP treatment.

| UI/external capability | Status | Evidence and implementation boundary |
|---|---|---|
| Partner authentication | VERIFIED | [Client credentials OAuth token](https://developer.hungerstation.com/api-specifications) is documented; cache token to `expires_in`, keep client secret server-side. The screen's one-click restaurant authorization/consent UX is UNVERIFIED; credentials come through Partner Portal/account manager. |
| Discover chain/business and all branches after connecting | UNVERIFIED / MOCK FOR MVP | Public guide tells partners to obtain `chain_id` and map vendor IDs; no general branch discovery/account consent endpoint identified. [Outlet guide](https://developer.hungerstation.com/en/documentation/outlet-management-api-how-to-integrate). Require supplied/mapped IDs until verified. |
| Retrieve vendor products and categories | VERIFIED | [GET vendor catalog and categories](https://developer.hungerstation.com/api-specifications) are documented, paginated and searchable. Restaurant catalog shape and localization remain unverified. |
| Async catalog export and result callback | VERIFIED | [POST catalog export](https://developer.hungerstation.com/api-specifications) and webhook result with job/download URL are documented. Protect callback and download ingestion. |
| Update product price, active flag and quantity | VERIFIED | [PUT vendor catalog](https://developer.hungerstation.com/api-specifications) requires SKU and at least one of `price`, `active`, `quantity`; returns 202/job ID. Active status also depends on quantity vs portal sales buffer. |
| Create a product, title, description or image | NOT PUBLICLY SUPPORTED for production / MOCK FOR MVP | [POST add products](https://developer.hungerstation.com/api-specifications) is marked beta, “Do NOT use in production,” pilot/market dependent and can return 501. It accepts such fields but does not justify a production edit workflow. Existing [PUT catalog](https://developer.hungerstation.com/api-specifications) documents only price/active/quantity. |
| Edit category assignment, modifier groups/add-ons, image crop/upload | NOT PUBLICLY SUPPORTED / MOCK FOR MVP | Read categories and product images exist; no public production edit endpoint for these fields found in the cited spec. Internal drafts only. |
| Read/update outlet open/closed status | VERIFIED | [GET/PUT vendor status](https://developer.hungerstation.com/api-specifications) document OPEN/CLOSED_TODAY/CLOSED_UNTIL/CHECKIN. This is outlet status, not individual product availability. |
| Full branch schedule, branch metadata import | UNVERIFIED / MOCK FOR MVP | Outlet overview mentions opening hours, but the reviewed public operations do not establish the screen's complete branch import/scheduling semantics. |
| Retrieve vendor order history for basic performance | VERIFIED | [GET vendor orders](https://developer.hungerstation.com/api-specifications) is paginated and date-filtered. Derived revenue/order metrics need reconciliation and permission; impressions/ROAS are not implied. |
| Create/update/deactivate strikethrough promotion | VERIFIED | [Promotion upsert](https://developer.hungerstation.com/api-specifications) documents `STRIKETHROUGH`, dates, vendors, products, async status. Confirm restaurant entitlement and exact accepted mechanics in sandbox. |
| Same-item bundle promotion | NOT PUBLICLY SUPPORTED for production / MOCK FOR MVP | The [promotion spec](https://developer.hungerstation.com/api-specifications) says `SAME_ITEM_BUNDLE` is work in progress and coming soon. A contract shape alone is not availability. |
| Custom mixed-item bundle/meal combo listing | NOT PUBLICLY SUPPORTED / MOCK FOR MVP | No public custom bundle catalog operation found; same-item promotion does not support the Stitch composition flow. |
| Promotion performance, uplift, attribution | UNVERIFIED / MOCK FOR MVP | Orders may expose promotion data, but the screen's attributed metrics and benchmark deltas require a defined data source and model. |
| Create/manage advertising campaigns, home banners, placements | NOT PUBLICLY SUPPORTED / MOCK FOR MVP | No advertising or placement operation found in the reviewed public Partner API. The `NMR` promotion reason mentioning supplier banners is not an ad management API. |
| Sponsored-search bid read/write, visibility share, ad spend/ROAS | NOT PUBLICLY SUPPORTED / MOCK FOR MVP | No bidding or advertising reporting contract found. Do not expose live publish controls. |
| Competitor/market prices, radius benchmarks, elasticity, recommendations | UNVERIFIED / MOCK FOR MVP | No approved market-intelligence source or AI provider supplied. Use licensed/provider boundary; label all seeded examples. |
| Async job status and callbacks | VERIFIED for documented catalog/promotion operations | [Catalog job status and callbacks](https://developer.hungerstation.com/api-specifications) exist; record `job_id`, feedback and retries. Completion does not automatically prove customer-visible state. |
| Read-back confirmation after a write | VERIFIED only for fields with a GET contract | Catalog and outlet GET can support comparison after async completion; exact propagation delay and customer-app visibility SLA are UNVERIFIED. |

## Critical product implication

The 18 screens are approved visual designs, but their live buttons exceed the public API. Implementation must gate each button by capability and account entitlement and say “Draft” or “Demo” when appropriate. The public documentation's Q-Commerce scope makes a restaurant pilot/access agreement the first integration milestone. No production API was called during this research.
